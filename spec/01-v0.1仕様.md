# v0.1 確定仕様 — 実装対象

**この文書だけを見て実装できるように書いています。** `reference/` 以下の仕様書は背景資料であり、v0.1 の実装対象ではありません。両者が食い違った場合は**この文書が正**です。

パッケージ名（仮）: `amp` / モジュール構成の提案は `02-作業手順.md` を参照。

---

## 1. 入力

実装するツールは2つの入力を取ります。

1. **語彙カタログ** (`catalog.json`) — IDから型・表示名を引くための辞書
2. **メッセージ** (`message.json` または JSONL) — 英文に変換する対象

出力は英文1行（文字列）です。

---

## 2. 語彙カタログの形式

```json
{
  "version": "0.1",
  "entries": [
    {
      "id": "entity:agent.b",
      "kind": "individual",
      "type": "type:agent",
      "label": { "en": "AI-B" },
      "proper": true
    },
    {
      "id": "type:agent",
      "kind": "type",
      "generic_label": { "en": "agent" }
    }
  ]
}
```

### entry のフィールド

| フィールド | 必須 | 対象 kind | 内容 |
|---|---|---|---|
| `id` | ✓ | 全部 | `ns:path` 形式。`ns` ∈ `entity` / `type`（v0.1 はこの2つのみ） |
| `kind` | ✓ | 全部 | `individual` / `type` |
| `type` | ✓ | individual | その個体の型ID |
| `parent` | — | type | 親の型ID。省略ならルート型 |
| `label` | `proper: true` のとき✓ | individual | 表示名。`{"en": "..."}`。普通名詞として扱う個体には不要 |
| `generic_label` | — | type | 普通名詞としての呼び名。`{"en": "file"}` |
| `proper` | — | individual | 固有名詞か。既定 `false` |

### ID の形式

- `^(entity|type):[a-z][a-z0-9_]*(\.[a-z0-9_]+)*$`
- **ドットは可読性のための慣習であり、階層の意味論を持ちません。** 型の親子関係は `parent` フィールドのみが表します（ADR-012）。`type:software.browser` の親が `type:software` であることは、`parent` に書かれていなければ成り立ちません。

### generic_label の解決

個体から普通名詞を得るときは、`type` → `parent` → ... と遡り、**`generic_label` を持つ最も具体的な型**の値を使います。

```
entity:x  type: type:software.browser
type:software.browser  generic_label: "browser"   ← これが使われる
  parent: type:software  generic_label: "software"
```

チェーンを遡っても `generic_label` が見つからない場合はエラー（§6）。

## 3. メッセージの形式

```json
{
  "protocol": "amp/0.1",
  "id": "msg-001",
  "conversation": "conv-1",
  "sender": "entity:agent.b",
  "receiver": ["entity:agent.a"],
  "timestamp": "2026-09-13T10:00:00Z",
  "act": "inform",
  "content": {
    "predicate": {
      "lemma": "send",
      "tense": "present",
      "polarity": "affirmative"
    },
    "roles": {
      "agent":     { "refs": ["entity:agent.b"] },
      "patient":   { "refs": ["entity:file.a"] },
      "recipient": { "refs": ["entity:agent.a"] }
    }
  }
}
```

### envelope

| フィールド | 必須 | 内容 |
|---|---|---|
| `protocol` | ✓ | `"amp/0.1"` 固定。異なる値はエラー |
| `id` | ✓ | メッセージID |
| `conversation` | ✓ | 会話ID |
| `in_reply_to` | — | 応答対象のメッセージID |
| `sender` | ✓ | `entity:` 形式 |
| `receiver` | ✓ | `entity:` の配列 |
| `timestamp` | ✓ | RFC3339 |
| `act` | ✓ | v0.2 は `"inform"` / `"request"` のみ。他はエラー(§9.3) |

`phase` は v0.1 では使いません（handshake がないため）。あってもエラーにせず無視します。

### predicate

| フィールド | 必須 | 値域 |
|---|---|---|
| `lemma` | ✓ | 動詞の原形 |
| `tense` | ✓ | `past` / `present` |
| `polarity` | — | `affirmative`（既定） / `negative` |
| `aspect` | — | `simple` のみ。省略可・既定 `simple`。他の値はエラー |

`future` は v0.1 では扱いません（`will` の挿入は `commit` の実装と一緒にやる方が自然なため）。

### roles

v0.1 が扱う役割は3つだけです。

| 役割 | 必須 | 英文での実現 |
|---|---|---|
| `agent` | ✓ | 主語 |
| `patient` | — | 直接目的語 |
| `recipient` | — | `to <X>` |

その他の役割（`instrument` / `source` / `location` 等）が含まれていたらエラー。v0.2 以降で追加します。

role の値は `{ "refs": [...] }` のみ。**`refs` に置けるのはカタログに定義済みの `entity:` IDだけ**です（ADR-021）。URIや裸の文字列は置けません。

`attitude` はあっても無視します（判断3）。

## 4. 生成アルゴリズム

以下の手順で1文を組み立てます。

**Step 1 — 検証**
`protocol` が `amp/0.1` か、`act` が `inform` か、`aspect` が `simple` か（あれば）、未知の role がないか、`tense` が正しいかを確認する。違反はエラー（§6）。

**Step 2 — 語彙解決**
`roles` に出てくる全ての ref をカタログから引く。1つでも見つからなければエラー（v0.1 は strict 固定。`query` モードは実装しない）。

**Step 3 — 名詞句の生成**
各 role について §5 の手順で名詞句を作る。

**Step 4 — 主語の人称・数を決める**
`agent` の refs が1件なら3人称単数、2件以上なら複数。

**Step 5 — 動詞句の生成**

| tense | polarity | 形 |
|---|---|---|
| present | affirmative | `lemma` を主語の人称・数で活用（3単現なら `-s`） |
| present | negative | `does not` / `do not` + `lemma`（原形） |
| past | affirmative | `lemma` の過去形 |
| past | negative | `did not` + `lemma`（原形） |

否定は **do-support**（`does not` / `do not` / `did not`）を使います。動詞自体は原形に戻ることに注意。

**Step 6 — 語順で連結**

```
<主語> <動詞句> [<直接目的語>] [to <recipient>]
```

`patient` / `recipient` は省略された場合そのまま飛ばす。

**Step 7 — 仕上げ**
文頭を大文字にし、末尾にピリオドを付ける。ただし**固有名詞の大文字小文字は変更しない**（"a.json" が文頭に来ても "A.json" にしない。文頭に来ないよう `agent` は必須にしてある）。

---

## 5. 名詞句の生成手順

role の `refs` から名詞句を作ります。

**Step A — 各 ref を分類する**
カタログから `proper` と `type` を引く。

**Step B — 分岐**

| 条件 | 生成 | 例 |
|---|---|---|
| refs が1件・`proper: true` | `label.en` をそのまま | `AI-B` / `a.json` / `Trueful` |
| refs が1件・`proper: false` | 冠詞 + `generic_label` | `a file` / `an index` |
| refs が2件以上・**全て** `proper: true` | label をカンマ区切り、最後は `and` | `a.json, b.json and c.json` |
| refs が2件以上・全て `proper: false`・同一型 | 数詞 + 複数形 | `3 files` |
| refs が2件以上・混在 | 型ごとにまとめ、`and` で連結 | `2 files and an index` |

**混在時のまとめ方**: 固有名の個体はそれぞれ独立した項として扱い、普通名詞の個体は型ごとに数える。並び順は `refs` の出現順（最初に現れた型の順）。

**数量は算用数字で出すこと**（`3 files`。`three files` にしない）。

**冠詞の a/an は音で判定すること**（綴りではない）。`an entity` / `a URI` / `an hour` / `a user`。ライブラリに任せてください（判断4）。

**複数形も例外に注意**（`file` → `files`、`index` → `indices` または `indexes`、`child` → `children`）。これもライブラリに任せます。`inflect` の既定に従い、ゴールデンテストがそれと食い違ったらゴールデンテストの方を直してください。

## 6. エラー

エラーは例外として送出し、以下を必ず含めること。

- エラー種別
- 問題のあるメッセージの `id`
- 問題のあるフィールドのパス（例: `content.roles.patient.refs[2]`）

| 種別 | 条件 |
|---|---|
| `UnsupportedProtocol` | `protocol` が `amp/0.1` でない |
| `UnsupportedAct` | `act` が `inform` でない |
| `UnsupportedAspect` | `aspect` が `simple` 以外 |
| `UnsupportedRole` | `agent` / `patient` / `recipient` 以外の role がある |
| `UnknownId` | ref がカタログにない |
| `NoGenericLabel` | `parent` を遡っても `generic_label` が見つからない（普通名詞が必要な場合のみ） |
| `MissingField` | 必須フィールドがない |
| `InvalidValue` | `tense` 等の値域違反 |

**エラーを握りつぶして「それらしい英文」を出さないこと。** 黙って間違った英文を出す方が、エラーで止まるより有害です（監査ログが用途なので）。

## 7. CLI

```
amp render --catalog catalog.json messages.jsonl
```

- `messages.jsonl` は1行1メッセージのJSONL。`-` で標準入力
- 出力は1行1英文
- エラー時は該当行を stderr に出し、終了コード 1。`--skip-errors` を付けたときのみ、その行をスキップして続行する

## 8. v0.1 の既知の制限

これらは**バグではなく、判断の結果**です（`00-判断書.md` 参照）。

- 語彙カタログは静的ファイルで、実行時に増やせない
- `query`の`gap`は`agent`/`patient`/`recipient`のみ。`time`/`location`は役割自体が未実装
- `query`にattitudeは未対応(confidence副詞を疑問文にどう乗せるか、根拠となる用例がまだない)
- `props`/`measurements`は単一refかつ非固有名詞のみ(§9.6)。複数refや固有名詞への付与は根拠となる用例がなく未対応
- `request`/`reject`/`failure`/`close`/`query`の外側動詞はaspect: simple固定(§9.5)。進行形・完了形は`inform`/`commit`のみ

以下は M6(MAGIでの実利用)で実際に不足が確認され、v0.2 で追加実装した。詳細は §9。

- ~~確信度や情報源（attitude）が英文に反映されない~~ → v0.2: confidence/evidence/necessity に対応(§9.2)
- ~~関係節などの入れ子構造が表現できない~~ → v0.2: `patient` role が深さ1の埋め込み節 `{"clause": {...}}` に対応(§9.1)。`agent`/`recipient` のclause化、深さ2以上は未対応
- ~~`inform`以外のactが使えない~~ → v0.2: 判断2の覆すべき条件(M4全通し)を満たしたので、ADR-011の7語彙(`inform`/`request`/`query`/`commit`/`reject`/`failure`/`close`)を全て実装した(§9.3〜§9.4)。疑問文は`query`で作れるようになったが、命令文(依頼ではなく命令)は引き続き未対応
- ~~進行形・完了形が使えない~~ → v0.2: `inform`/`commit`で aspect: progressive/perfect に対応(§9.5)
- ~~未来時制が使えない~~ → `commit`の`will`で解決済み(判断書が想定していたとおり、未来時制は`will`の実装=commitとセットで足された。`inform`に別途`tense: future`は追加していない — 同じ表層形("will send")を2つの経路で作る必要がないため)
- ~~形容詞・測定値が使えない~~ → v0.2: `props`/`measurements`に対応(§9.6)

## 9. v0.2 追加分(reference/open-issues-remaining.md R-4 / 判断3 への対応)

### 9.1 content の再帰(R-4)

`patient` role の値は `{"refs": [...]}` の代わりに `{"clause": {content}}` を取れる。`content` は通常のメッセージの `content` と同形(`predicate` + `roles`)。英文では `"that " + <埋め込み節の生成結果>` として挿入する。

```json
"patient": {
  "clause": {
    "predicate": { "lemma": "adopt", "tense": "present" },
    "roles": { "agent": { "refs": ["entity:claude"] }, "patient": { "refs": ["entity:amp"] } }
  }
}
```
→ `"... that Claude adopt amp."`(mandative subjunctive。下記参照)

制約:
- 深さ上限は1。埋め込み節の中にさらに `clause` を入れると `InvalidValue`
- `agent` / `recipient` は `clause` を取れない(`UnsupportedRole`)。役割自体を命題にする用途がまだ実例として出ていないため
- `refs` と `clause` を同時に持つ role、どちらも持たない role は `InvalidValue` / `MissingField`
- **外側の lemma が mandative動詞**(`recommend` / `suggest` / `insist` /
  `demand` / `require` / `propose` / `request` / `ask`)**のとき、埋め込み節は
  必ず原形(bare infinitive)で生成する**(例: `Claude adopt amp`。`Claude
  adopts amp` にはしない)。indicative(時制活用)のままだと「まだ起きて
  いない、提案されている行為」を「事実」として述べる形になり、JSON側の
  意味(推奨であって事実ではない)と英文の意味がずれる ── これは本仕様が
  防ごうとしている曖昧さそのものなので、閉じた語彙リストとして明示的に
  扱う(判断4の対象である屈折の例外とは別種の話)。上記以外の lemma
  (`inform`・`state` 等)では埋め込み節は通常どおり時制活用する

### 9.2 attitude(confidence / evidence / necessity)

`reference/spec-revised.md` §3.7・§4.4 のとおり実装。`attitude` はメッセージの**トップレベル**フィールド(`content` の兄弟)で、省略可。

```json
"attitude": { "confidence": 0.9, "evidence": "inferred", "necessity": "should" }
```

| フィールド | 値域 | 英文での実現 |
|---|---|---|
| `confidence` | 0.0〜1.0 | 1.0=なし / 0.85以上=almost certainly / 0.65以上=probably / 0.5以上=possibly |
| `evidence` | observed(なし) / inferred(Apparently,) / reported(Reportedly,) / assumed(Presumably,) | 文頭副詞 |
| `necessity` | may / should / must | 動詞の前の法助動詞。この場合、動詞は時制活用せず原形のまま |

語順固定: `[evidence副詞,] 主語 [confidence副詞] [法助動詞] 動詞 ...`

**`inform` の confidence は0.5以上でなければならない**(`InvalidValue`)。0.5未満を送りたい場合は `polarity` を反転し `confidence` を `1 - c` にして送る(呼び出し側の責務。amp は自動変換しない)。

`attitude` は top-level のみで、§9.1 の埋め込み節自身は attitude を持たない。

### 9.3 `request` act(判断2への対応)

判断2の「覆すべき条件」(M4全通し)を満たしたので追加した2つ目の act。
`reference/spec-revised.md` §4.1 の worked example をそのまま実装している。

```json
{
  "protocol": "amp/0.1", "id": "...", "conversation": "...",
  "sender": "entity:agent.a", "receiver": ["entity:agent.b"],
  "timestamp": "...", "act": "request",
  "content": {
    "predicate": { "lemma": "send", "tense": "present" },
    "roles": {
      "agent":     { "refs": ["entity:agent.b"] },
      "patient":   { "refs": ["entity:file.a", "entity:file.b", "entity:file.c"] },
      "recipient": { "refs": ["entity:agent.a"] }
    }
  }
}
```
→ `"AI-A requests AI-B to send a.json, b.json and c.json to AI-A."`

**新しいフィールドは追加していない。** `content.roles` は `inform` と全く同じ意味(agent=要請された行為をする者/patient=その目的語/recipient=行き先)のまま流用し、「要請する側」は envelope の `sender` から取る。二重の `recipient` を発明していない ── `recipient` は常に「要請された行為の行き先」だけを指し、「要請の宛先」は `sender` → `agent` という既存の envelope/content 構造だけで表現できる。

- `predicate.lemma` は要請された行為の動詞。**常に原形**("to send")。tense/polarity は `request` という行為自体に付く(例: `tense: past, polarity: negative` → `"AI-A did not request AI-B to send a.json."`)
- `agent` role は必須(誰に何をしてほしいかが request の本体のため)。`patient`/`recipient` は inform と同様に省略可
- `patient`/`agent`/`recipient` いずれも `clause`(§9.1)は未対応。要請された行為自体が複文になるケースはまだ実例が出ていない
- attitude(§9.2)はそのまま乗る。necessity は「requestすること自体」への法助動詞になる(例: `"AI-A must request AI-B to send a.json."`)

### 9.4 残り5act(`query`/`commit`/`reject`/`failure`/`close`)

判断2の「act を1つずつ足す」方針どおり、request(§9.3)に続けて残り5つも
`reference/spec-revised.md` §4.1/§4.2 の worked example をそのまま実装した。
新しいフィールドは `query` の `gap`(既存仕様どおり)のみで、他は全て
`content.roles` を inform と同じ意味で流用している。

| act | 例文 | 備考 |
|---|---|---|
| `query` | `Does AI-B send 3 files to AI-A?` | tense/polarityに応じ`Do`/`Does`/`Did`+`[not]`+原形。文末は`?`(`.`ではない) |
| `commit` | `AI-B will send 3 files to AI-A.` | `will`は内部的にattitude.necessityと同じ機構で挿入する法助動詞。実際の`necessity`と衝突するので同時指定は`InvalidValue` |
| `reject` | `AI-B refuses to send 3 files to AI-A.` | `refuse`をtense/polarity/数で活用し、`to <lemma>`を続ける。requestと違い要請者は要らない(agentが行為者=拒否する本人) |
| `failure` | `AI-B failed to send 3 files to AI-A.` | rejectと同型、outer動詞が`fail` |
| `close` | `AI-A ends the conversation.` | 主語はenvelopeの`sender`。`content.roles`は取らない(あれば`UnsupportedRole`)。目的語("the conversation")は固定文言でカタログを引かない |

**`query`の`gap`**(§4.2、新フィールド):

```json
{ "act": "query", "gap": "patient", "content": { "predicate": {...}, "roles": { "agent": {...}, "recipient": {...} } } }
```

| `gap` | 例文 |
|---|---|
| なし | `Does AI-B send 3 files to AI-A?` |
| `agent` | `Who sends 3 files to AI-A?`(`agent`をrolesから省略。whoは常に単数扱いでdo-support無し) |
| `patient` | `What does AI-B send to AI-A?`(`patient`をrolesから省略) |
| `recipient` | `To whom does AI-B send 3 files?`(`recipient`をrolesから省略) |

`gap`に指定した role が `content.roles` にも残っていたら `InvalidValue`。`gap: "time"` / `"location"` は該当する role が v0.2 にまだ存在しないため `InvalidValue`(自前で仮の意味を割り当てない)。`query` に `attitude` を付けると `InvalidValue`(confidence副詞を疑問文の語順にどう乗せるか根拠となる用例がまだないため、実装せず明示的に拒否する)。

**`reject`/`failure`が`request`と構造が違う理由**: `request`は「誰が誰に何をしてほしいか」で3者(要請者=sender/行為者=agent/対象)必要だが、`reject`/`failure`は「行為者が行為をしなかった/できなかった」という1人称的な事実なので、agentが主語兼行為者を兼ねる。2つを同じ形にすると、どちらか一方が不自然になる。

### 9.5 aspect: progressive / perfect

`predicate.aspect` に `progressive`(進行形)・`perfect`(完了形)を追加した。**`inform`と`commit`のみ**対応する(`request`/`reject`/`failure`/`close`/`query`の外側動詞はaspect: simple固定のまま — 「requestという行為自体」が進行中/完了しているという文は用例がなく、無理に対応範囲を広げない)。

| aspect | 肯定 | 否定 |
|---|---|---|
| `progressive` | `is`/`are`/`was`/`were` + V-ing | 同 + `not` + V-ing |
| `perfect` | `has`/`have`/`had` + V-en | 同 + `not` + V-en |

`simple`と違い、progressive/perfectの助動詞(be/have)は肯定文でも常に出る(do-supportのように否定のときだけ現れるのではない)。法助動詞(necessity)や埋め込み節の原形化(mandative subjunctive、§9.1)とも両立する:

- `"AI-B should have sent a.json."` (necessity + perfect)
- `"AI-B recommends that AI-A be sending a.json."` (mandative + progressive)
- `"AI-B will be sending a.json."` (commitの`will` + progressive)

### 9.6 props / measurements(形容詞・測定値)

`reference/spec-revised.md` §3.8 のとおり実装。role の値に `props`(スケールなし属性のID配列)・`measurements`(スケールあり属性→測定値のマップ)を追加できる。

```json
"patient": {
  "refs": ["entity:file.a"],
  "props": ["prop:encrypted"],
  "measurements": { "prop:size": { "value": 4.2, "unit": "unit:gigabyte" } }
}
```
→ `"...an encrypted 4.2 GB file..."`

catalogに`kind: "property"`(必須: `scaled`)・`kind: "unit"`(必須: `quantity`)を追加できる。`scaled: false`なプロパティは`props`に、`scaled: true`なプロパティは`measurements`にのみ置ける(逆はInvalidValue)。

**閾値**: `type`エントリに`thresholds`を持たせると、測定値が条件を満たしたとき数値の代わりに形容詞を使う(例: `"a large file"`)。`generic_label`と同じく`parent`チェーンを遡り、最も具体的な型の閾値定義を使う。

```json
{ "id": "type:file.text", "kind": "type", "parent": "type:file",
  "thresholds": { "prop:size": [
    { "below": { "value": 1, "unit": "unit:megabyte" }, "label": { "en": "small" } },
    { "above": { "value": 100, "unit": "unit:megabyte" }, "label": { "en": "large" } }
  ]}}
```

**単位変換はしない(v0.2の意図的な制限)**: 閾値とのマッチは`unit`が完全一致したときだけ行う。4.2 GBの測定値をMB単位の閾値と比較して自動換算することはしない(単位を跨いだ比較を実装すると、変換テーブルの正しさという新しい曖昧さの温床を持ち込むことになるため)。単位が一致しなければ閾値は無視され、測定値をそのまま出す(`"a 4.2 GB file"`)。閾値自体が定義されていない型でも同様。

**制約**: `props`/`measurements`は**単一ref・非固有名詞のときのみ**。複数refでは「3件のうちどれが大きいのか」、固有名詞では「"an encrypted Trueful"の冠詞は要るのか」が未定義のため、どちらも`InvalidValue`(実例が出てから設計する)。
