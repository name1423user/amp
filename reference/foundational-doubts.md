# AMPは本当に成立するのか — 全項目への回答

`semantics-gap-analysis.md`(30項目)が「完成に向けた課題」の棚卸しだったのに対し、
これは「**AMPという設計思想そのものが成立するか**」を疑う視点で出された全項目への回答。
量が多いため、先に5つの判定ラベルを定義し、各項目をそれに当てはめる。同じ答えを
170回書くのではなく、根っこが同じ項目は同じラベルの下にまとめる。

## 判定ラベル

| ラベル | 意味 |
|---|---|
| **[構文]** | AMPが実際に排除を目指す統語論的曖昧性の範囲内。解決済み、または通常の機能追加で解決できる |
| **[接地]** | **記号接地問題(symbol grounding problem)**。AMP固有の欠陥ではなく、自然言語を含むあらゆる記号システムが共有する原理的限界。「外側に曖昧さを移動している」のではなく「外側にあるべきものを正しく外側に置いている」 |
| **[先送り]** | 技術的には解決可能だが、ADR-024(実例が出るまで拡張しない)により意図的に未実装 |
| **[検証不能]** | 判断書の核心認識どおり、単一実装では原理的に検証できない(第二の独立実装が必要) |
| **[圏外]** | AMPのメッセージフォーマットの責務ではなく、上位プロトコル・運用ルール・受信側AIの実装の責務 |

## 根本的な課題

| # | 項目 | 判定 |
|---|---|---|
| 1 | 曖昧性排除と正しい意味表現の区別 | **[構文]** ADR-023で明文化済み |
| 2 | 「曖昧でない」の定義 | **[構文]** 「同一のJSON構造から一意に1つの統語論的解釈しか導けないこと」。意味の中身の一意性ではなく構造の一意性、と定義する |
| 3 | 「意味が同じ」の判定基準 | **[先送り]** canonical formが無く一般的な等価性判定アルゴリズムは無い。ADR-024の一本化で個別ケースを潰しているだけ |
| 4 | 自然言語の意味を有限構造へ落とし込めるか | **[接地]** 原理的に不可能(自然言語は無限生成的)。AMPは自然言語の意味全体を捉える野心を持たない——「AI間で必要な範囲の主張を構造化する」がスコープだと明示すべき |
| 5 | 表現できない意味が発生した場合の扱い | **[先送り]** 現状は「送らない」以外の代替経路(自然言語へのフォールバック等)が無い |
| 6 | 表現できないことと間違って表現したことの区別 | **[構文]** 前者はエラー(`UnsupportedXxx`)、後者はADR-023の範囲外(真偽の問題)。既に区別できている |
| 7 | 現実世界とAIの世界モデルの区別 | **[接地]** AMPは後者(送信者の世界モデル内の主張)のみを扱う。ADR-023の帰結 |
| 8 | AMPが記述するのは現実か送信者の認識か | **[構文]** ADR-023で確定済み: 送信者の主張(locutionary act)。現実かどうかは保証しない |

## 文脈

| # | 項目 | 判定 |
|---|---|---|
| 49 | AMP単体で意味が完結しないメッセージ | **[構文/圏外]** `in_reply_to`で前後関係は辿れるが、それを辿らないと意味が確定しないメッセージを許容するかは設計判断。現状は許容している(Phase 1のqueryがそうだった) |
| 50 | 過去メッセージを参照する表現 | **[先送り]** `in_reply_to`はメッセージ単位の参照のみ。メッセージ内の特定の値(「そのfile」)を指す照応の仕組みは無い |
| 51 | `this`/`that`/`it`のような指示対象 | **[構文として意図的に排除]** AMPの設計そのものが「指示は`refs`でカタログIDを明示する」ことで指示代名詞を最初から締め出している(ADR-021)。つまりこの項目は「課題」ではなく「AMPが解決した対象そのもの」 |
| 52 | 会話履歴によって変わる意味 | **[先送り]** 50番と同根 |
| 53 | メッセージ順序が意味に影響する場合 | **[検証不能]** gap-analysis 27番。トランスポート層の順序保証に依存 |
| 54 | 同じentity名が異なる会話で意味を持つ場合 | **[先送り]** ADR-014(語彙は会話スコープ)により、原理的には会話をまたいで同じIDが別の対象を指すことはカタログ設計次第で起こりうる。カタログ側の規律に委ねられている |
| 55 | 会話状態をどこまでAMPに含めるか | **[圏外]** 含めない、が設計判断(ステートレスなメッセージの連続として設計されている)。状態はオーケストレーター(呼び出し側)が持つ(Phase 2で実証済み) |
| 56 | 文脈を失ったAMPを別AIが読んだ場合の意味 | **[構文]** カタログと`in_reply_to`さえあれば単体で解釈可能なように設計されている。カタログが無ければ`UnknownId`でエラーになる(黙って誤読しない) |

| 81 | AMPを知っているAI同士でも同じ意味に解釈する保証 | **[検証不能]** gap-analysis 4・23番。判断書の核心認識そのもの |

| 83 | AIが仕様に存在しない意味を補完する問題 | **[検証不能]** 同上。仕様の記述漏れ(今回発見した`close`のpredicateの扱いなど)がある限り起こりうる |

| 85 | AIがAMPの一部を無視する問題 | **[構文]** `_check_known_roles`等の実装によりreceiver側(パーサ)は無視しないが、AI自身が「読んだのに無視して応答する」ケースは防げない |
| 86 | AIが未知フィールドを勝手に解釈する問題 | **[構文]** 実装は未知roleを`UnsupportedRole`で拒否する(spec §6)。AI自身のフィールド生成段階での混入は82番と同じ |
| 87 | AIが構文的には正しいが意味的に不正なAMPを生成する問題 | **[検証不能]** ADR-023が明示的に許容している事態そのもの |

## 他方式との差別化

個別に判定ラベルを付けるより、まとめて答える方が正確。

| 方式 | AMPとの関係 |
|---|---|
| **AMR(Abstract Meaning Representation)** | 自然言語**理解**(パース結果)のための表現。AMPは逆方向——AI自身が最初から構造化された主張を**生成**する前提で、自然言語解析を経由しない(ADR-001で意図的に除外)。目的が違う: AMRは既存テキストの意味を取り出す道具、AMPは意味を最初からJSONとして持つための道具 |
| **Semantic Role Labeling** | AMPのrole(`agent`/`patient`/`recipient`)はSRLの意味役割をそのまま借用している。**新規性はここにはない**。AMPが足しているのは、SRLには無いact(発話行為の種類)・attitude・envelope(会話管理)という上位の層 |
| **RDF / Knowledge Graph** | RDFは静的な事実の集合(トリプルストア)を表現する。AMPは**時間発展する会話**(誰が誰にいつ何を言ったか)を表現する。「今から何をするか/してほしいか」という発話行為の概念がRDFには無い |
| **FIPA ACL / KQML** | 直接の先祖。act語彙(inform/request/query等)・sincerity assumptionの発想はここから継承している。**違いはスコープの絞り方**——FIPA ACLは20種以上のperformativeとhandshake相当の交渉プロトコルまで含む大きな仕様だが、AMPは判断書の哲学(単一実装では検証できないものを作らない)により7語彙・handshakeなしまで削っている |
| **MCP(Model Context Protocol)** | 層が違う。MCPはAIとツール/データソースの接続を規定するプロトコル(縦の接続)。AMPはAI同士の発話内容の意味を規定する(横のメッセージの中身)。MCPのメッセージのペイロードとしてAMPを載せることは矛盾しない |
| **A2A(Agent2Agent Protocol)** | A2Aはエージェント間のタスク委譲・状態同期などトランスポート/オーケストレーションの層を規定する。AMPはR-1(open-issues)で明言している通りトランスポート層を規定しない。A2Aのメッセージ本文としてAMPを使う、という組み合わせが自然な棲み分け |
| **JSON Schema / Protocol Buffers** | これらは**構文**(型・必須フィールド)を検証する道具であり、AMPが要求する**意味論**(act、attitude、mandative subjunctiveのような英文生成規則、時制やclauseの解釈規則)までは持たない。AMPのスキーマ検証をJSON Schemaで書くことは可能(むしろ書くべき)だが、それはAMPの半分(構文層)にすぎない |
| **既存技術の組み合わせで同じものが作れるのでは** | 作れる。実際AMPはSRL(role)+FIPA ACL(act)+RDF的なentity/catalog+JSON Schema(検証)の**組み合わせ**であり、個々の要素に新規性は無い。**AMPの新規性は「AI間の監査可能な発話行為」という一点に全てを絞り込み、handshakeや多者間会話のような検証不能な部分を意図的に削ぎ落とした、その削り方**にある。技術要素の再発明ではなく、スコープの再設計 |
| **AMPが既存技術より優れる具体的な場面** | 「AI同士のやり取りを、人間が監査できる自然文として機械的に復元する」場面。既存技術(RDF/ACL単体)はこの英文生成を主目的にしていない。Phase 1・2の実証はまさにこの場面 |
| **既存技術の再発明になっていないか** | 部分的にはなっている(role, act語彙)。ただし判断書が最初から「仕様として十分詰まっている」ことを認めた上で「実装がないから使えない」という状態を問題にしていたので、**車輪の再発明であることは自覚済みで、価値は車輪の組み合わせ方と、検証可能な範囲への絞り込みにある**と整理するのが正直な答え |

## 最大の検証課題への回答

> AMPが「曖昧性を排除している」のか、それとも「曖昧性をJSONの外側へ移動させているだけ」なのか

**両方が同時に真であり、これは矛盾ではなく正しい設計の姿だと考える。**

AMPが実際に排除しているのは**統語論的曖昧性**——同じメッセージが複数の構造的解釈を
許すこと。自然言語の "send the file to me" は、誰が送るか(主語が省略されている)、
どの `file` か(候補が複数あれば一意に定まらない)、いつ送るか、が構文上一意に決まらない。
`agent`/`patient`/`recipient`/`tense` を明示するAMPは、この種の曖昧さを構造として
解消する。これは実際に排除できている——ADR-021(`refs`はカタログ済みIDのみ)がこの
排除の実装そのもの。

しかし `file.a` が指す実体が何か、"send" が意味する状態変化が何かという**意味の中身
(記号接地)** は、AMPの外部——カタログ、共有された世界知識、運用上の合意——に依存する。
これは「移動」ではなく「**正しい責任分界点**」だと考える。理由は、この記号接地問題
(symbol grounding problem)はAMP固有の欠陥ではなく、**自然言語を含むあらゆる記号
システムが共有する原理的限界**だから。自然言語の "file.a" という単語も、結局は
話者間の共有知識・慣習・直示(deixis)に依存して指示対象を固定しており、単語それ自体が
意味を内包しているわけではない。AMPだけがこの限界を持つわけではない。

重要なのは、AMPが「どこまでを構造で保証し、どこから先を外部に委ねるか」の**境界線を
明示していること**。ADR-021は「file.aとは何か」という問題を、メッセージ内部の曖昧さ
から「カタログ」という名前のついた明示的な契約に**切り出した**。これは曖昧さの隠蔽
ではなく、**曖昧さの所在を名指しした**ことに等しい。ADR-023(構文の曖昧性排除≠内容の
真偽の保証)は、この同じ切り分けを別の軸(構造 vs 真偽)でもう一度行ったものであり、
両方とも同じ設計原則の異なる現れだと言える。

したがって正確な言い方は:

> **AMPは統語論的曖昧性を排除する。記号接地(記号が現実の何を指すか)の問題は排除
> できないし、そもそも排除を目指していない。ただしAMPは、その未解決部分を「カタログ」
> 「attitude」「confidence」のような、明示的に名前のついた外部依存として切り出すことで、
> 少なくとも『どこに未解決性が残っているか』自体は曖昧にしない設計になっている。**

これをADR-025として明文化する価値がある——ADR-023(構文≠真偽)、ADR-024(一本化≠拡張)
に続く3本目の「AMPの保証範囲」原則として。
