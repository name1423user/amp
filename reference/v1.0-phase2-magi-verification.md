# v1.0 Phase 2検証: MAGI 3体合議をAMPで運用

`v1.0-goal.md` の検証方法のうち「MAGIの3体合議にAMPを組み込み、3体が実際にAMPメッセージで
主張・反論・収束を行う」を実施した記録。Phase 1([`v1.0-roundtrip-verification.md`](v1.0-roundtrip-verification.md))
がAMP単体(2エージェント・4-5メッセージ)の検証だったのに対し、Phase 2は
MAGI型合議(3エージェント・独立評価→相互反論→収束)という、より複雑な社会的構造をAMPで
表現できるかを見る。

## 方法

`magi-decide`スキル(軽量版)のRound 1(独立評価)〜Round 2(相互反論)に相当する部分を、
3体の独立したサブエージェント(`entity:agent.utility`/`entity:agent.quality`/
`entity:agent.validation`)で実施した。Fact Reconciliation・Sensitivity Analysis・
Adversarial Auditなどのフルプロトコルは実施していない——Phase 2の目的は「AMPが
3体間協調のメッセージ運搬手段として機能するか」であって、MAGIプロトコル自体の
再現ではないため。

題材は自己言及的に選んだ: 「ampはPhase 1でv1.0を達成した。次に何をすべきか」を
4択(A: MAGI本格導入を続ける / B: 第二の独立実装を探す / C: ADR-024で先送りにした
拡張に先行着手する / D: PyPI公開の周知に注力する)で3体に評価させた。

カタログ: [`examples/magi-v2-catalog.json`](../examples/magi-v2-catalog.json)
メッセージ: [`examples/magi-v2-messages.jsonl`](../examples/magi-v2-messages.jsonl)

## 結果

```
$ amp render --catalog examples/magi-v2-catalog.json examples/magi-v2-messages.jsonl
Utility recommends Option A (proceed to MAGI integration).
Quality probably recommends Option B (seek a second independent implementation).
Apparently, Validation almost certainly recommends Option B (seek a second independent implementation).
Apparently, Utility probably recommends Option A (proceed to MAGI integration).
Quality probably recommends Option B (seek a second independent implementation).
Apparently, Validation probably recommends Option B (seek a second independent implementation).
```

Round 1でUtility=A、Quality/Validation=Bと割れ、Round 2で相互に反論をぶつけた結果、
**形式的な推奨(A/B)は変わらなかったが、実質的な対立は解消した**——3体とも
「AとBは排反ではなく並行して進めるべき」という点で一致した(詳細は下記Final Decision)。
新しい反論・新情報が出なくなったため、magi-decision-001.mdと同じ基準でSTOP判定とした。

## 見つかったバグ・仕様の穴

**Round 1で実際に仕様違反のAMPメッセージが生成され、`amp render`が正しく検出した。**
Quality役が最初に生成したメッセージは`attitude`を`content`の中にネストして置いており
(仕様は`content`の兄弟)、かつ`confidence`に`"high"`という文字列を入れていた
(仕様は0.0〜1.0の数値)。

```
InvalidValue: InvalidValue in message 'magi2-quality-r1' at 'attitude.confidence': got 'high'
```

これは判断書の「エラーを握りつぶして『それらしい英文』を出さないこと」がまさに機能した
瞬間であり、AMPが単なる作文ツールではなく検証機構として動くことを実地で確認できた。
Quality役に仕様の該当箇所(§9.2)を示して修正を依頼したところ、独立した2つの経路
(元のサブエージェントの継続 / 新規サブエージェント)がどちらも同じ正しい修正
(`attitude`をトップレベルに移動、`confidence`を数値に変更)に収束した——同じエラーから
同じ修正パターンが再現することも確認できた。

**なお、このミスはgap-analysis項目4(フィールド解釈の同一性保証)の実例そのもの**:
仕様書を読ませても、AIがフィールドの配置を読み違えることがある。今回は`amp render`という
決定的な検証手段があったために発覚し訂正できたが、この検証手段が無い(=英文レンダリング
のような形式的チェックを持たないメッセージ交換)場合、この種の誤りは検出されないまま
伝わっていた可能性が高い。

## Final Decision(要約)

- **decision: conditional** — Option A(MAGI本格導入の継続)とOption B(第二の独立実装への
  呼びかけ開始)を**並行して**進める。Bは実現までのリードタイムが長く他者依存のため、
  今すぐ着手を開始する価値がある一方、Aは自分の手番で継続でき、ADR-024が要求する
  「実例」を運用しながら生み出せる
- Option C(先行拡張)・Option D(周知)は3体とも明確に劣後と判定
- **veto**: なし
- **robustness: medium** — 3体は独立したサブエージェントとして起動したが、全員が
  同じ入力資料(`v1.0-goal.md`・`semantics-gap-analysis.md`等)を読んでおり、
  magi-decision-001.md(各自が異なる一次情報にHTTPアクセス・grep実行で到達)ほどの
  evidence diversityは無い。この点は今回の実験設計の限界として記録する

## v1.0-goal.mdとの照合

Phase 2は「3体が実際にAMPメッセージで主張・反論・収束を行う」ことを実証した。
Phase 1と合わせて、v1.0の検証方法2つのうち両方を満たしたことになる。

**Phase 1との違いで分かったこと**: 2者間の逐次会話(Phase 1)では状態参照
(前のcommitを覚えてqueryする)が検証の中心だったが、3者間の並行合議(Phase 2)では
**同じactが複数のエージェントから同時多発的に送られ、互いを参照しあう**という、
Phase 1にはない構造が出てきた。AMPの`in_reply_to`は1対1の応答関係しか表せないため、
「Round全体としての収束」という多対多の関係は、AMPメッセージ自体ではなく
オーケストレーター(呼び出し側)が`conversation` ID越しに全メッセージを集めて
判断する必要がある。これは仕様の欠陥ではなく、`magi-decide`スキル自身が
「Fact Reconciliation以降は呼び出し側が統合する」と明記している設計と一致する。
