# 実験E: 条件節の最小構造(削除実験)

実験B(experiment-b-comparison-matrix.md)で「AMPには条件節を表す構造が無い」
ことが2ケースで実証された。ADR-024の手順(既存構造で表現不可を確認→最小候補を
設計→削除実験で要否を検証)に従い、`condition`という最小構造を仮設計し、
「あり/なし」で同じメッセージをB役に解釈させて比較した。

## 仮設計(この実験限りの一時的な定義。まだ仕様化していない)

```
content.condition(省略可): {
  "type": "until" | "after" | "if",
  "clause": { "predicate": {...}, "roles": {...} }
}
```

既存の`patient.clause`(§9.1)と全く同じ形(predicate + roles)を流用し、
配置場所と意味だけを追加した——新しい構文要素を発明せず、既存要素の再利用に
留めている点はADR-024の「一本化」の精神に沿う。

## シナリオ

「AI-Aが確認するまでは、AI-Bはfile.aを送ってはいけない」
(実験Bの"Don't send until Alex confirms it"を、既存カタログの語彙だけで
表現できるよう単純化: 確認する主体をAI-A自身にした)

## 結果(削除実験)

| バージョン | B役の解釈(自己申告) |
|---|---|
| **condition無し**(禁止のみ: `must not send`) | 「file.aを永久に送ってはいけないのか、何らかの条件が満たされるまでなのか、この情報だけからは**判断できない**」 |
| **condition有り**(`type: "until"` + `clause`) | 「`condition.type: "until"`が明示されているため、**判断できる**——`clause`(AI-Aがfile.aを確認する)が真になるまでの条件付き禁止であるとこのメッセージ自体から読み取れる」 |

**自己評価が「判断できない」から「判断できる」へ、`condition`フィールド1つの
有無だけで劇的に変わった。** これはminimal-form-experiment.mdで見出した
「AI自身が申告する精度低下」を、逆方向(構造を足して精度が回復するか)で
検証したことになり、同じ手法が両方向に機能することも確認できた。

## 意義

これでADR-024が要求する手順が全部完了した:

1. 既存構造(roles/clause/attitude)で表現できないことを実験Bで確認済み
2. 最小候補(`condition: {type, clause}`)を設計
3. 削除実験で「本当に意味の一意性を回復するか」を検証 → **回復した**

これは「実例が出たら着手する」というADR-024の条件を満たしている。ただし、
これは1シナリオ・1回の削除実験に過ぎない。仕様化する前に、少なくとも以下は
未検証:

- `type: "after"`/`"if"`のケースでも同様に機能するか
- 英文生成のルール(until節をどう英語化するか——`"AI-B must not send file.a to
  AI-A until AI-A confirms it."`のような文型が必要になり、これはrender.pyに
  新しい構文生成ロジックを要求する)
- `condition`と`clause`(patient)が同じメッセージに同時に現れた場合の扱い
- `agent`/`recipient`の`clause`と同様、`condition`の`clause`にも深さ制限や
  mandative動詞的な特殊ルールが要るか

## 次にやるなら

- ここでは仕様化(spec更新・実装)は行わない。まず`type: "after"`のケースでも
  同じ削除実験を1回試し、`condition`という抽象化が"until"固有ではなく
  汎用的に機能するか確認してから、判断書と同じ形式のADR(仮称ADR-026)として
  正式な設計判断に格上げするのが筋
