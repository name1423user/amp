# 「削る」実験: AMPの最小核を探る

## 背景

これまでの実験(gap-analysis, foundational-doubts, Gemini blind test, independent
implementation experiment)は一貫して「何が足りないか」を探す方向だった。しかし
independent-implementation-experiment.mdとgemini-blind-test.mdが示したのは、
AMPには少なくとも3つの層が混ざっているということ:

- **A. 意味構造化** — act・predicate・roles(誰が誰に何を、という骨格)
- **B. 英語レンダリングの規約** — confidence閾値→副詞のような、AMP独自の恣意的変換
- **C. 通信プロトコルとしての体裁** — handshake・語彙合意(判断1により最初から未実装)

gemini-blind-test.mdは「Bが無くても意味は伝わる(数値をそのまま説明された)」ことを
示した。であれば、Bはおそらく核心ではない。Cは元から実装していない。**残る問いは、
Aの中のどこまでが本当に必要か**——ここで初めて「足りないものを探す」から
「なくても成立するものを削る」方向に転換した。

## 方法

Phase 1([`v1.0-roundtrip-verification.md`](v1.0-roundtrip-verification.md))と同じ
シナリオ(AI-BにAI-A宛のfile.a送信を依頼する)を、**tense・polarity・attitude・
clause・aspectを一切使えない最小フィールド**だけで、独立したサブエージェント2体に
やらせた。

```json
{
  "act": "request",
  "content": {
    "predicate": { "lemma": "send" },
    "roles": {
      "agent": {"refs": ["entity:agent.b"]},
      "patient": {"refs": ["entity:file.a"]},
      "recipient": {"refs": ["entity:agent.a"]}
    }
  }
}
```

(実装上はenvelopeの`id`/`conversation`/`sender`/`receiver`は残した——通信の
最低限のメタデータとして削る対象にしていない。削ったのは`content`側のみ。)

## 結果(4ターン)

| # | act | 内容 | 送信側の自己申告 |
|---|---|---|---|
| min-001 | request | B→file.aをA宛に送って | 「依頼の強さ・丁寧さは表現できない」 |
| min-002 | commit | Bが送ると約束 | 「未来/進行中/完了の区別がつかない。actの種類自体に未来志向を代弁させた」 |
| min-003 | query | Aが状況確認 | **「正確に表現できていない。requestとほぼ同じ見た目になった」** |
| min-004 | inform | Bが応答 | 「送信済みか進行中か表現できない」 |

## 発見

**1. actの選択そのものが、tenseが無くても意味の大半を運ぶ。**
`commit`は「これから送る約束」を、`request`は「送ってほしい依頼」を、tense無しでも
明確に伝えた。これはFIPA ACL系のact語彙が、そもそも時間軸に依存しない発話行為の
分類であることの証拠——act自体が持つ情報量は高い。

**2. しかし同じactの中の時間的区別は失われる。**
A役は「まだ送っていないか確認したい」というmin-003を作る際、`query`+同じlemma
(send)という形が、min-001の`request`とほぼ同じ見た目になってしまうと**自分から
報告した**。tenseがあれば`Did AI-B send file.a?`(過去形の疑問文)として一意に
区別できていたところが、無いと構造的な曖昧さに戻る。

**3. それでも会話は破綻しなかった——会話履歴という文脈が曖昧さを吸収した。**
B役はmin-003を見て、それが新規の要求ではなく状態確認だと**誤解せずに**正しく
解釈した。理由は「contentが自分の直前のcommitと完全に一致していたから」。つまり
tenseという構造的な保証が無くても、**同じ会話の中で内容が繰り返し参照される限り、
文脈が意味を補完する**。これはPhase 1で確認した「conversation内の状態保持」が、
tenseの代替としてある程度機能することを示している。

**4. AIは表現の不正確さを、自分から申告した。**
4回中3回、送信側のエージェントは「これは正確に表現できていない」と自己申告した。
一度も会話は完全に破綻しなかったが、精度が落ちていることをAI自身が自覚していた。
これは仕様の必要性を判定する新しい手がかりになる——**「会話が壊れるかどうか」
だけでなく「AI自身がどれだけ自信を持ってその表現を選べたか」も、フィールドの
要不要を測る指標になりうる。**

## 暫定的な結論

`tense`は完全に無くしても、**シンプルな1対1の会話は致命的には壊れない**
(文脈が補う)。ただし、AI自身が精度の低下を自覚しており、以下のような
より複雑な状況では破綻する可能性が高い(未検証、次にやるなら):

- 複数の`request`/`query`が同じ会話で並行して進行している場合(文脈が一意に
  定まらなくなる)
- 3者以上の会話(誰の発言に対する状態確認かが曖昧になる)
- 長い会話で、同じlemmaを使った過去のやり取りが複数回登場する場合

`polarity`(否定)・`attitude`・`clause`・`aspect`は今回のシナリオでは
一度も必要にならなかった——これは「無くても最低限は動く」ことの実証だが、
M6(MAGI dogfooding)で`attitude`/`clause`の必要性が既に実証されている
(m6-magi-findings.md)こととは矛盾しない。**必要性はフィールド単体の
性質ではなく、シナリオが要求するかどうかで決まる**、という当たり前だが
重要な確認になった。

## 示唆: 仕様追加の判定基準

ユーザー提起の「AMPは作りすぎていないか」という疑いに対する暫定的な回答:

- v0.1コア(tense/polarity/roles 3つ)は、Phase 1のような「状態を参照する
  会話」で実際に必要性が確認された(tenseを削ったら劣化が実証された)
- v0.2拡張(attitude/clause/aspect/props/measurements)は、MAGI実運用で
  個別に必要性が確認された機能ばかりで、"あり得るケースを想像して先回りで
  足した"ものではない——ADR-024の「実例が出るまで拡張しない」は実際に
  守られてきている
- したがって「作りすぎ」という疑いは、少なくとも**現在実装済みの範囲については
  裏付けが弱い**。各機能は個別に実運用またはこの実験で必要性の証拠がある

ただし、今回の実験は1シナリオ・1往復半に限られる。判定基準として今後も
使えるのは「新しいフィールドを追加する前に、まずそれを削った最小形で
実際に会話させ、AI自身が申告する精度低下を観察する」というプロトコル。
これは今後の拡張判断(gap-analysisで先送りにした7・8・9・10・18〜22番)にも
そのまま使える。
