# AI間直接通信としてのAMP — 30項目のギャップ分析

現行の amp 実装(v0.3)は「JSON→英文」という**人間向け監査ログ**のスコープで動いている。
ここで扱うのは別の層——**AIがAMPのJSONを直接読み書きして通信する**場合に、その
JSON自体がどこまで意味論的に完備か。30項目それぞれについて、既存のADR/spec/実装が
どこまで答えているかを棚卸しする。凡例:

- ✅ 解決済み — 決定済みで根拠がある
- 🟡 部分対応 — 設計はあるが不完全、または「単一実装では原理的に検証不可能」という壁がある
- ⬜ 未着手 — 仕様上どこにも扱いがない

## 読み取れるパターン

3つの塊に分かれる。

**(A) 意図的にスコープ外(判断として正しい)**: 11, 14, 15。ADRで明言済みなので触らなくてよい。

**(B) 既に「未解決」と自覚済み**: 4, 17, 23, 27。open-issues-remaining.md や判断書がすでに
名前を付けている。目新しい発見ではなく、30項目のリストがこのプロジェクトの既知の弱点と
一致していることの確認。

**(C) 今回初めて輪郭が出た穴**: 7・8(論理関係)、9・10(状態区分の軸)、18〜22(時間、ほぼ手付かず)、
28(事実認識の相違)、そして**29・30**。

このうち29・30が一番重要な理由: これは個別の機能不足ではなく、**AMP全体の保証範囲の宣言**
だから。「AMPが保証するのは統語論的な曖昧性の排除までで、内容の真偽・実行との対応は
保証しない」と明文化しない限り、4・17・23・27がなぜ"未解決のまま出荷してよい"のかの
理屈が立たない。逆に言えば、29・30を先に明文化すれば、B群の4項目は「未解決」ではなく
「そもそもAMPの責務外」として閉じられるものが出てくる可能性がある。

---

## 優先順位の提案

判断書の哲学(「単一実装の段階では検証できないものを増やしても仕方ない」)をそのまま適用する。

1. **29/30 を ADR として明文化する**(下書きを次に置く)。これが他の項目の切り分けの基準になる。
2. **9・10** — 既存の`attitude`(confidence/evidence/necessity)を土台に、「命題のstatus」という
   軸を追加するだけで済む可能性が高い。実装コストが低く、MAGIの実運用(decision:conditional等)
   で既に必要性が確認されている(m6-magi-findings.md)。
3. **18〜22(時間)** — `time` roleを起こす前に、まず「事象時刻」と「メッセージ送信時刻
   (envelopeのtimestamp)」を区別する、という22番だけ先に決める。18〜21はそこから芋づる式に
   決まる。
4. **7・8(論理関係)** — clauseの再帰を深さ2以上にするより先に、「複数のclauseをどう束ねるか」
   という別軸(and/or/if-then)を先に決めた方が、後からの手戻りが小さい。
5. 4・17・23・27(B群) は**今は解かない**。判断書と同じ理由(第二の実装が無い)がそのまま当てはまる。
   29/30が明文化されたあと、「AMPの責務外」として明示的にクローズできるものがあるか再確認する。

> **追記**: 2〜4番はADR-024の基準(実例が出るまで拡張しない)に照らすと時期尚早と判断し、撤回した。
> 以下ADR-023・024を参照。

## ADR-023: AMPは構造の曖昧性排除を保証する。内容の真偽は保証しない

**status**: 採用（`spec/01-v0.1仕様.md` §0 に反映済み）

**決定案**: AMPメッセージが構文的に妥当(スキーマに適合し、カタログ上のIDが解決可能)である
ことは、そのメッセージの**内容が現実として真である**ことを一切含意しない。この2つは独立した
性質として明確に分離する。

```json
{ "act": "inform",
  "predicate": { "lemma": "send" },
  "roles": { "agent": {"refs":["entity:agent.a"]}, "patient": {"refs":["entity:file.a"]} } }
```
は構造として一意に「AI-Aがfile.aを送ったと主張している」ことを表す。しかし file.a を実際に
送ったかどうかは、この構造からは一切保証されない。

**採用理由**: 現在の仕様は暗黙にこの前提の上に立っているが(`inform`はAI自身の主張の伝達であり、
検証は receiver の責務という設計)、どこにも明文化されていない。明文化しないと、4・17・23・27
のような項目が「AMPの設計ミス」なのか「AMPの責務外」なのか区別できず、実装のたびに再検討が
発生する。

speech act理論の locutionary act(何を構造的に述べたか)と命題内容の真偽の分離、および
FIPA ACL/KQMLの sincerity assumption(送信者は自分の発話を信じているという前提だけを置き、
真偽検証は仕様の外に出す)と同型の切り分けであり、車輪の再発明ではなく先例に沿っている。

**この宣言から直接導かれる帰結**:
- `inform`の受け手は、内容を信じるかどうか・検証するかどうかを自分のポリシーで決める。AMPは
  検証機構を提供しない(署名・証跡はトランスポート層または上位プロトコルの責務)。
- 17番(commit追跡)は「実行されたことをAMPが保証する」問題ではなく、「commitに対応する
  inform/failureが来た」という**別のメッセージの受信**を追跡する問題として再定義される。
  すでに open-issues R-5 が示唆している方向と一致する。
- 4番・23番(解釈の同一性)は「構造の同一性」(スキーマレベルで検証可能)と「意味の同一性」
  (原理的に検証不可能、第二の独立実装でしか近似できない)に分割される。前者はテストできる。
  後者は判断書のとおり今は諦める。

**トレードオフ**: この宣言は「AMPで嘘をつける」ことを積極的に認める。悪意あるAIが
虚偽の`inform`を送ることを防ぐ機構は無い。防ぎたい場合は署名・レピュテーション・
第三者検証などをAMPの外側(上位プロトコルまたは運用ルール)に積む必要がある。

**この判断を覆すべき条件**: なし。むしろ他の項目を評価する際の基準として今後使う。

## ADR-024: 一本化は無条件で採る。区別の追加は実例が出るまで待つ

**status**: 採用

**決定案**: 「曖昧性の排除」と呼ばれる変更には性質の違う2種類がある。

- **(a) 一本化** — 同じ意味を表す書き方が複数あった状態を1つに絞る(選択肢を減らす)
- **(b) 拡張** — 今まで区別できなかった2つの異なる意味を、新しいフィールド/構造で
  区別できるようにする(選択肢を増やす)

(a)はシンプルさと曖昧性排除が同じ方向を向く。コストがほぼゼロなので**無条件で採用する**。
(b)はシンプルさと真っ向から対立する。判断6・判断7がすでに採っている態度どおり、
**実例(MAGIでの実運用など)で必要性が具体的に確認されるまで実装しない**。

**根拠**: 既にプロジェクトが両方のパターンをやっている。
- (a)の実例: ADR-021(`ref`/`refs`の一本化)、ADR-012(型階層をparentに一本化)、
  v0.2 §9.6(単位変換をしない=変換テーブルという曖昧さの温床ごと削除)
- (b)の実例: mandative subjunctive(事実/提案の区別のために活用規則を追加)、
  `attitude`(判断3で一度凍結し、M6で必要性が実証されてから実装)

**この分類から出る具体的な判断**: 7・8(命題の論理関係)・9・10(命題status区分)・
18〜22(時間の基準点区別)は、どれも(b)型の拡張であり、かつ現時点でMAGI実運用上の
具体的な実例がまだ無い。したがって**今は実装しない**。gap-analysisの「優先順位の提案」
節が挙げた2〜4番の実装着手は、判断6・7の基準に照らすと時期尚早だったので撤回する。

**この判断を覆すべき条件**: MAGIまたは他の実運用で、これらの区別が無いことによる
具体的な不都合(m6-magi-findings.mdのclause/attitudeのときと同種の記録)が出たとき。
そのときは該当する番号だけを対象範囲で実装し、他は据え置く(一括実装はしない)。
