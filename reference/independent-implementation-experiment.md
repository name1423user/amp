# 疑似独立実装の実証実験(Gemini/JavaScript)

「第二の独立実装が現れるまでhandshakeを実装しない」(判断書 判断1)という前提の裏返しとして、
「そもそも第二の実装は仕様書だけから実際に作れるのか」を検証した記録。本物の独立実装
(第三者が独自の動機で書く)ではないが、コードベース・言語・モデルベンダーが完全に
異なる2実装を比較する、という点では近似的な検証になる。

## 方法

Gemini(Web UI, ログインなし, Flash-Lite)に、`spec/01-v0.1仕様.md`のv0.1コア部分
(§0〜§6、v0.2拡張の§9は除外)を丸ごと貼り付け、**Pythonの実装コードは一切見せずに**
「この仕様に基づいてNode.jsでrender(message, catalog)関数を実装してください。外部
npmパッケージなし、屈折処理も自分でルールを書いてください」とだけ指示した。

## 結果

一発生成されたコードをそのままファイルに保存し、Pythonの`tests/golden.jsonl`のうち
v0.1コア範囲(act: inform、attitude/clause/aspect拡張なし、22件)を、実際に
Python実装が使っているのと同じカタログ(`examples/catalog.json`、v0.2以降の
`prop:`/`unit:`エントリを除いたもの)で流した。

```
tested=22 pass=22 fail=0
```

**22/22、完全一致。** 手直し・デバッグは一切行っていない。

途中で1回全滅した(`Invalid entity ID format: prop:encrypted`)が、原因はGemini実装の
バグではなく**こちら側のテスト設計のミス**——`examples/catalog.json`はv0.2で追加された
`prop:`名前空間を含む「フルカタログ」なのに、Geminiには「v0.1は`entity`/`type`のみ」
という仕様しか渡していなかった。Geminiはその仕様に忠実に`prop:`を無効なIDとして拒否
した。カタログをv0.1範囲(`entity:`/`type:`のみ)に絞ったら全通過した。この失敗自体が
「仕様書どおりに厳格な検証をしている」ことの傍証になっている。

## 何が実証されたか、何が実証されていないか

**実証されたこと**: `spec/01-v0.1仕様.md`は「この文書だけで実装できる」という自己申告
(冒頭の一文)どおりの完成度を持っている。全く異なるモデル(Gemini Flash-Lite)・
全く異なる言語(JavaScript、外部ライブラリなし)・全く異なる実装判断(不規則動詞
テーブルの持ち方、grouping処理の構造)で書かれたコードが、屈折処理(3人称単数の-s、
不規則動詞sent/built、冠詞のa/an判定、複数形化、固有名詞の列挙分岐)という判断書が
「一番の難所」と位置づけた部分を含めて、Python版と1文字も違わない出力を生成した。

**実証されていないこと**: これは本物の独立実装ではない。(1)仕様書自体をこちらが
書いている(第三者が独自に仕様を定めたわけではない)、(2)スコープをv0.1コアに
絞っている(v0.2以降のact 7語彙・attitude・clause・props/measurementsは未検証)、
(3)1回のテスト実行であり、Geminiに複数回同じ指示をした場合の再現性は見ていない。
gap-analysis項目4・23(スキーマ解釈の同一性は単一実装では検証不可能)が指す
「本当の実用化条件」は、依然として満たされていない——これはあくまで「仕様書の
明確さ」の検証であって、「独立に開発された実装との相互運用性」の検証ではない。

## 追試: 再現性(同じ仕様・同じ指示を3回)

「たまたま1回だけ良い実装が生成された」可能性を排除するため、全く同じプロンプトを
新規チャット(前回の文脈を持ち越さない)で3回投げ、3つの独立したコードを得た。

| 実行 | golden test(v0.1コア22件) |
|---|---|
| 1回目 | 22/22 |
| 2回目 | 22/22 |
| 3回目 | 22/22 |

**3回とも全通過。** 3つのコードは実装判断が毎回違う(非proper要素のグループ化に
`Map`を使うか配列を使うか、正規表現の書き方、不規則動詞テーブルの持たせ方など)にも
かかわらず、golden testの出力は1文字も違わず一致した。これは「仕様書から実装への
解釈空間がかなり狭い」ことを支持する証拠であり、単発の偶然ではないと言える。
