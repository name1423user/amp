# AMP思想レビューに基づく改善提案書

作成日: 2026-09-14 / 対象: 現行仕様(`spec/01-v0.1仕様.md`, v0.3相当) + `reference/` 全実験・分析記録

**この文書は提案書であり、この提出をもって仕様・コードを変更しない。** 各提案には根拠(実験・記録)を明示し、
「追加しない」という結論も対等な成果として扱う。

---

## 1. AMPの基本思想の再評価

ユーザー提示の思想 ——

> AI同士が意思疎通する際に、自然言語だけでは誤解しやすく、かつ誤解すると困る意味を、必要最小限だけ構造化して明示する。

—— を基準に既存資料を読み直すと、**この思想は今回新しく導入するものではなく、このプロジェクトが既に自力で到達していた設計原則そのもの**だと分かる。根拠:

- [`foundational-doubts.md`](foundational-doubts.md) #4:「自然言語の意味を有限構造へ落とし込めるか」→「AMPは自然言語の意味全体を捉える野心を持たない——AI間で必要な範囲の主張を構造化する、がスコープ」
- [`semantics-gap-analysis.md`](semantics-gap-analysis.md) ADR-024:「一本化(選択肢を減らす)は無条件で採る。区別の追加(選択肢を増やす)は実例が出るまで待つ」
- 判断書(`amp-handoff/amp-handoff/00-判断書.md`)全体:「単一実装の段階では検証できないものを増やしても仕方ない」という一貫した縮小志向

つまり本提案書がやるべきことは「思想を新規に持ち込んで既存仕様を裁く」ことではなく、**既にADR-024として明文化されている基準を、ユーザー提示の①〜⑤の手順として再確認し、実際にそれが守られているか棚卸しすること**である。結論を先に言うと、後述のとおり**概ね守られている**。逸脱があるとすれば「守りすぎて足りていない」方向(condition等の追加検討がADR-024の基準を満たしたのに正式化が止まっている)であり、「表現力を広げすぎた」方向の逸脱は見当たらなかった。

## 2. 改善の判断基準の適用

ユーザー提示の5段階(①問題の実在→②自然言語で解決不可か→③誤解コスト→④既存構造で表現不可か→⑤最小の追加)は、[`v2-goal-necessity-proof.md`](v2-goal-necessity-proof.md)が定めた「仕様追加のサイクル」

```
問題発生(実験で表現できない/誤解される)
  → 既存の最小構造で表現できるか再確認
  → できない
  → 新フィールドを設計
  → 削除実験で本当に必要か検証
  → 仕様化
```

とほぼ同型である。以下の全評価は、この歯止めをそのまま適用した結果である。新しい基準を持ち込んでいない。

## 3. 現在のAMPの3分類

| 分類 | 項目 | 根拠 |
|---|---|---|
| **A. コアとして維持** | `refs`によるentity参照の一意化(ADR-021) | 実験F/F-2/G/L3-matrix/cross-model-verificationで再現された唯一の「自然言語に対する実証済みの優位性」 |
| | 7語彙の`act`(inform/request/query/commit/reject/failure/close) | ADR-011、dogfooding round2で6/7が実データ通過、minimal-form-experimentで「actだけでtense無しでも意味の大半が伝わる」ことを確認 |
| | `agent`/`patient`/`recipient`の3role固定 | Phase1・Phase2・全実験で一度も不足が実証されていない |
| | `tense`(past/present)+`polarity`+do-support | 実験Aで4/4往復、無誤読 |
| | `attitude`(confidence/evidence/necessity) | v0.2でM6実運用の実害から追加、v1.0 Phase2で誤配置を`amp render`が実際に検出 |
| | `aspect`(progressive/perfect)、`clause`深さ1 | dogfooding round2で実データ通過、m6-magi-findingsで実運用の必要性実証 |
| | ADR-023(構文≠真偽)・ADR-024(一本化は無条件/拡張は実例待ち) | 個々のフィールドではなく、AMP全体の保証範囲を定めるメタ原則。B群の項目群(相互運用性未検証等)が「未解決のまま出荷してよい」理屈の土台 |
| **B. 検討すべき(実例あり・検証不足)** | `condition`(until/after/if) | 削除実験(experiment-e)で1シナリオのみ検証済み、「自己評価が判断不可→判断可能に反転」という明確な効果。ただしtype別の追試が未実施 |
| | `time` role(事象時刻とメッセージ時刻の区別) | 複数実験(B/D/G試行2)で従属節が丸ごと脱落することを確認済みだが、gap-analysisが提案した「まず22番だけ先に決める」という最小の切り口自体、ADR-024の基準に照らして時期尚早と一度撤回されている |
| | be動詞+補語構文(述語位置の形容詞) | dogfooding round2で実際に1回困った(`amp exists`への簡略化を強いられた)。実例1件のみ |
| **C. 現時点で追加しない** | urgency | 実験Aで1件のみ脱落を確認。最小構造の候補すら未設計 |
| | 論理演算(AND/OR/NOT/IF/ELSE/UNLESS/XOR)、clauseの入れ子(深さ2以上) | 実例ゼロ。後述§6・§7参照 |
| | tone/nuance(丁寧さ等) | 実験Cで「意図的に保持しないことが機能している」ことを実証済み。追加は逆行 |
| | 語用論的動機(pragmatic meaning) | l3-matrix/cross-model-verificationでモデル間の評価基準の違いが観測され、AMPが一意化できる対象ではないと判明 |
| | 否定と情報不在の区別、命題status(仮説/事実/意見)区分 | ADR-024で「2〜4番の実装着手は時期尚早と判断し撤回」と明記済み。今回の再調査でも撤回を覆す新しい実例は無い |

## 4. 個別評価: 12項目

凡例 — 誤解コスト/AMP追加価値: 高・中・低。推奨: 維持/実験/追加しない。

### entity reference

| 項目 | 内容 |
|---|---|
| 現在の表現能力 | `refs`はカタログ済み`entity:`IDのみを取り、代名詞・URI直書きを構造的に排除(ADR-021) |
| 問題 | 現状ほぼ無し。今回の再調査でも新たな欠落は見つからなかった |
| 実験証拠 | 実験F(1件)・F-2(4件)・G(3件目)・level-difficulty-scaling(Level1-4)・L3-matrix(候補数2/3/4)・cross-model-verification(Sonnet/Gemini)——**独立した6本の実験群で再現**。「entity数」ではなく「自然言語側の参照手がかりの競合」がある場合にのみ差が生まれることまで特定済み |
| NLとの比較 | NLは直近性・pronoun等の表面手がかりに依存し、競合時に誤読または判定拒否が発生(NL 1/4正解のケースあり) |
| 誤解コスト | 高(誤ったファイル・誤った相手を操作しうる、まさにユーザーが冒頭で挙げた懸念そのもの) |
| AMP追加価値 | 高。**唯一、複数の独立実験で再現された「AMPが自然言語より優れる」条件** |
| 推奨 | **維持**。AMPの存在意義の中心。追加変更は不要 |

### agent / patient / recipient

| 項目 | 内容 |
|---|---|
| 現在の表現能力 | 3role固定。動詞ごとに異なるroleフレーム(FrameNet的な可変role)は持たない |
| 問題 | 理論上は「動詞によって必要なroleが違う」(gap-analysis #9/10)が指摘されているが、実運用でこれが原因の誤解は一度も報告されていない |
| 実験証拠 | Phase1(5メッセージ)・Phase2(3体合議)・M6・dogfooding round2の全実運用で3roleのみで破綻せず動いた |
| NLとの比較 | NLは`instrument`/`source`/`location`等を自由に使えるが、その分曖昧性のリスクも負う |
| 誤解コスト | 中(理論上はあるが実例なし) |
| AMP追加価値 | 低(現時点) |
| 推奨 | **維持**。ADR-024の「実例が出るまで拡張しない」をそのまま適用 |

### act

| 項目 | 内容 |
|---|---|
| 現在の表現能力 | 7語彙(inform/request/query/commit/reject/failure/close)、1メッセージ1act前提 |
| 問題 | 複合speech act(「確認してほしい、かつ結果を教えてほしい」等)が1メッセージで表現不可(gap-analysis #13/32/33) |
| 実験証拠 | dogfooding round2で6/7 actが実データ通過。複合actの必要性を示す実例は**まだゼロ** |
| NLとの比較 | NLは自然に複合発話行為を1文で表現できる |
| 誤解コスト | 中(複数メッセージへの分割で回避可能、実害の実証なし) |
| AMP追加価値 | 低 |
| 推奨 | **維持**。7語彙で十分。複合actは実例が出てから検討 |

### predicate

| 項目 | 内容 |
|---|---|
| 現在の表現能力 | `lemma`(原形)+`tense`(past/present)+`polarity`+`aspect`(simple/progressive/perfect) |
| 問題 | ①lemmaの多義性(英語の意味論に暗黙依存)、②be動詞+補語構文(「AがBという状態である」)を表現する経路がない(実際に発生: `dogfooding-round2.md`) |
| 実験証拠 | ①は理論的指摘のみ([接地]判定、foundational-doubts #11)。②はdogfooding round2で実データにより1件確認 |
| NLとの比較 | ①はNLも同じ限界を共有(自然言語の多義性そのもの)。②はNLなら自然に書ける |
| 誤解コスト | ①低(自然言語も共有する限界)。②中(実際に1回困り、簡略化を強いられた) |
| AMP追加価値 | ①低。②中、ただし実例1件のみ |
| 推奨 | **維持**(現状の`predicate`構造)。be動詞+補語は**実験**(次に実例が出たら`predicate`に`copula`的な最小拡張を検討) |

### tense / aspect

| 項目 | 内容 |
|---|---|
| 現在の表現能力 | past/present、future(`commit`の`will`で代替)、simple/progressive/perfect |
| 問題 | ほぼ無し。当初懸念された「進行形・完了形」はv0.2で実運用実証済み |
| 実験証拠 | 実験A(4/4往復、tense/aspectの取り違え無し)、minimal-form-experiment(tenseを外すと4回中3回で送信側が精度低下を自己申告→tenseの必要性の裏付け) |
| NLとの比較 | NLは時制を自然に表現できるが、pronoun等と組み合わさると曖昧化しうる。AMPは構造的に一意 |
| 誤解コスト | 高(時制の取り違えは重大)だが解決済み |
| AMP追加価値 | 高、既に実現 |
| 推奨 | **維持** |

### urgency

| 項目 | 内容 |
|---|---|
| 現在の表現能力 | 表現不可。対応するフィールドが存在しない |
| 問題 | 実験Aで実際に脱落——「今すぐ(right now)」という緊急性を、送信側AI自身が「対応する構造がないので正直に諦める」と判断し削った |
| 実験証拠 | 実験Aの1件のみ。再現性の検証なし |
| NLとの比較 | NLは容易にurgencyを表現でき、**ここはAMPが自然言語に明確に劣る領域**として実証されている |
| 誤解コスト | 中〜高(緊急度の誤解は対応順位を誤らせる可能性があるが、実例は1件) |
| AMP追加価値 | 中。ただし最小構造の候補すらまだ設計されていない |
| 推奨 | **実験**。次の削除実験の対象として最有力(§9のロードマップ参照)。今すぐ仕様化はしない |

### condition

→ 詳細は§5で単独に扱う。結論のみ: **検討すべき(B)**、ただし最小形の追試が先。

### temporal relation(時系列・前後関係)

| 項目 | 内容 |
|---|---|
| 現在の表現能力 | 表現不可。`time` role自体が未実装(spec §8) |
| 問題 | 実験D(簡易)・実験B・実験G試行2で"after"/"right after"のような従属節が丸ごと脱落することを確認 |
| 実験証拠 | 中。実験Dは簡易実施のみ。実験G試行2は本来の争点(entity参照)を汚染する形で偶発的に再現しており、専用の検証ではない |
| NLとの比較 | NLは相対時間表現が豊富。ここもAMPが劣る領域 |
| 誤解コスト | 中〜高(期限の取り違えは重大) |
| AMP追加価値 | 中。gap-analysisは一度「事象時刻とメッセージ時刻の区別だけ先に決める」という最小案を提示したが、ADR-024の再評価で「実例不足のため時期尚早」と自ら撤回した経緯がある |
| 推奨 | **実験**。ただしconditionの検証が優先(condition側で必要になる`type: "after"`の検証が、time roleの必要性の実例としても機能する可能性が高い——同じ調査で両方に知見が得られる) |

### negation

| 項目 | 内容 |
|---|---|
| 現在の表現能力 | `polarity: affirmative/negative`、do-support実装済み |
| 問題 | 否定 vs 情報不在の区別がない(gap-analysis #9)。複合命題の否定(ド・モルガンの法則が絡むもの)は未対応 |
| 実験証拠 | 単純否定は実験Aで実証済み(4/4往復、誤読なし)。情報不在との混同が実際の会話で問題になった実例はまだ無い |
| NLとの比較 | NLも「知らない」と「〜でない」を混同しやすい場面があり、これはAMP固有の弱点ではない |
| 誤解コスト | 中(理論上は閉世界仮定の問題だが実例なし) |
| AMP追加価値 | 低。ADR-024が既に「時期尚早」として撤回済みの項目 |
| 推奨 | **維持**。単純否定で十分 |

### uncertainty / epistemic state(attitude)

| 項目 | 内容 |
|---|---|
| 現在の表現能力 | `confidence`(0.0-1.0→副詞)、`evidence`(4値→文頭副詞)、`necessity`(法助動詞) |
| 問題 | 自己申告値の検証不能性(confidence 0.7を両者が同じ確信度として扱う保証がない、gap-analysis #94/110-112) |
| 実験証拠 | 強い。M6実運用で必要性が実証され追加、v1.0 Phase2で**実際に`attitude`の配置ミス(contentの中にネスト)をAI自身が起こし、`amp render`がInvalidValueで検出**——検証機構として機能することを実証 |
| NLとの比較 | NLの"probably"等も同じ主観性を持つ。検証不能性はAMP固有の欠陥ではなく、自然言語を含む記号システム全体が共有する限界([検証不能]、ADR-023のsincerity assumptionと同型) |
| 誤解コスト | 高(意思決定の文脈では致命的)。ただし検証不能性そのものはAMPの責務外として明確に切り分け済み |
| AMP追加価値 | 高、既に実現 |
| 推奨 | **維持** |

### tone / nuance

| 項目 | 内容 |
|---|---|
| 現在の表現能力 | 意図的に非対応 |
| 問題 | 無し。実験Cで「命令形/丁寧命令/必要性表明/疑問依頼」の4表現が**完全に同一のJSON構造に収束**し、丁寧さの混入が0/4であることを確認——これは"欠陥"ではなく設計の成功として記録されている |
| 実験証拠 | 強い(実験C) |
| NLとの比較 | NLはトーンを自然に保持する。AMPは意図的にこれを捨てている |
| 誤解コスト | 低。監査ログ用途ではagent/patient/recipient/actが一致していれば実務上の誤解は生じない |
| AMP追加価値 | **負**。追加すればむしろ実験Cが示した収束性という価値を損なう |
| 推奨 | **追加しない**。明確にAMPの責務外と位置づける |

### pragmatic meaning(語用論的意図・発話の動機)

| 項目 | 内容 |
|---|---|
| 現在の表現能力 | 非対応。`act`+`content`はlocutionary act(何を構造的に述べたか)のみを扱う(ADR-023) |
| 問題 | entity参照が一意でも、「なぜこの質問をしているのか」という動機は別に曖昧なまま残ることがある(experiment-l3-matrix「注意点」) |
| 実験証拠 | 中。cross-model-verificationのC軸で、Sonnetは「対象が一意でも動機は複数解釈可能」、Geminiは「対象が一意なら動機も一意」と評価基準自体がモデルによって異なることが判明——**AMPが一意化できる対象ではない**ことの証拠 |
| NLとの比較 | NLも語用論はもともと曖昧(比喩・皮肉と同種の限界) |
| 誤解コスト | 中(だがact+contentが一意なら実務上は十分というケースが大半) |
| AMP追加価値 | 低([圏外]。foundational-doubts #19/80/90が示すAMPの意図的なスコープ外) |
| 推奨 | **追加しない**。自然言語+受信側AIの推論に委ねる |

## 5. conditionについて — 短絡しない検討

conditionは実験B(2ケース)・D(簡易)・G試行2(偶発的再現)で失敗が確認された、今回の調査で最も裏付けの強い「実例あり」項目である。だが「表現できない→フィールドを追加する」への短絡は避け、以下を個別に検討する。

### どの種類の条件が本当に必要か

実際に確認された失敗は2種類のみ:

1. `"Don't send until Alex confirms it."` — 完了待ち条件(until)
2. `"Send the file to Alex after he finishes his review."` — 前後関係(after)、ただしこのケースは実際には条件節の中の主語照応(pronoun)問題に吸収されてしまい、条件節そのものの必要性の実例としてはやや弱い

削除実験([experiment-e-condition-structure.md](experiment-e-condition-structure.md))で検証したのは`until`のみ、1シナリオ。**`if`(仮定条件)は一度も実例が出ていない**。

### 単純な条件だけで十分か

削除実験の仮設計は以下で、これが必要十分な最小形だと考える:

```
content.condition(省略可): {
  "type": "until" | "after" | "if",
  "clause": { "predicate": {...}, "roles": {...} }
}
```

既存の`patient.clause`(§9.1)と全く同じ形(predicate+roles)を流用しており、**新しい構文要素を1つも発明していない**。これはADR-024の「一本化」の精神(既存要素の再利用)にそのまま合致する。

### conditionの中にさらにconditionを入れる必要があるか

**不要と判断する。** 実例が一件も無い。`clause`が既に「深さ上限1・節の中に節は不可」という制約を持っており(v0.2 §9.1)、`condition.clause`にも同じ制約を適用すれば十分。二重条件("AがBするまで、かつCが起きなければ")のような入れ子が必要になった実例が出た時点で再検討する。

### AND / OR / NOTなどの論理演算まで必要か

**不要と判断する。** これは§6で述べる「AMPがプログラミング言語化する危険」そのものであり、以下の理由で明確に拒否する:

- 実例がゼロ(実験B/D/G試行2はすべて単一の条件のみで、複数条件の論理結合は一度も要求されていない)
- 論理演算子を1つ入れると、次は「条件式のネスト」「優先順位」「短絡評価」……と要求が芋づる式に増える、まさにユーザーが懸念する「表現力の拡大が目的化する」経路
- 複数条件が本当に必要になった場合でも、**複数メッセージへの分解**(「Xが起きたら送る」「Yが起きたら送るな」を別々のconditionメッセージとして送る)で当面代替できる。これは実験Bが指摘した「一体的な意味の結びつきが失われる」というコストを払うが、そのコストが実際に問題になった実例はまだ無い

### AMPがプログラミング言語化する危険はないか

`condition: {type, clause}`という最小形自体にはその危険は無いと判断する。理由: `type`は3値の閉じた語彙(until/after/if)であり、`clause`は既存構造の再利用に留まっている。危険が生じるのは、ここにAND/OR/NOT、ネスト、優先順位を追加した瞬間からである。**したがって「conditionを追加するかどうか」と「conditionに論理演算を持たせるかどうか」は別の問題として扱い、後者は明確に拒否する。**

### 自然言語との併用で十分ではないか

実験A・Bが示した通り、AMPは「表現できない情報を、捏造せず正直に落とす」という一貫した挙動を取っている(送信側AI自身が「対応する構造がない」と判断して省略した)。この挙動自体は健全だが、条件節に関しては実験Eが「有無だけで自己評価が判断不可→判断可能に反転する」という無視できない効果量を示しており、**「自然言語側で運用上カバーする」を単純に是とするには、実験Eの結果と矛盾する**。

### 結論(最小限第一候補)

> **`condition: {type: "until"|"after"|"if", clause: {predicate, roles}}` を追加候補(分類B)とする。ただし今すぐ仕様化はしない。** 削除実験は`until`の1シナリオのみで、`after`/`if`での追試が未実施であり、ADR-024が要求する「実例」の条件(複数type・複数シナリオでの再現)をまだ完全には満たしていない。experiment-e自身の「次にやるなら」が既にこの追試を予定しており、本提案はそれをそのまま次のアクションとして採用する(§9ロードマップ)。AND/OR/NOT、入れ子は明確に「追加しない」(分類C)。

## 6. 「表現力を増やすこと」を進歩としない、という原則の確認

このプロジェクトは既にこの原則を体現している。最も明確な証拠は**実験C**である——4つの言い回し(命令形・丁寧命令・必要性表明・疑問依頼)がAMP化した瞬間に完全に同一のJSON構造へ収束し、丁寧さの差は一切残らなかった(0/4)。これは「表現力の損失」ではなく、「必要な意味(誰が誰に何をするか)だけを残し、不要な変異(言い回しの揺れ)を吸収する」という設計が実際に機能している証拠として記録されている。

AND/OR/NOT/IF/ELSE/UNLESS/XORのような論理演算子群の追加は、この原則と正面から対立する。現状のAMPが持つ強さ——「見た瞬間に構造が分かる」「英文に一意に射影できる」——は、語彙が閉じていることに由来する。論理演算子はJSON上は数行の追加で済むように見えるが、それを英文として正しく生成する規則(条件が複数ある場合の語順、否定を含む論理式の英語化、優先順位の明示方法)は、動詞の屈折より遥かに大きな設計空間を持つ。判断書 判断4が屈折処理について警告した「自前でルールを書くと必ず破綻する、しかも発見が遅れる」という懸念が、論理演算の英文生成規則ではさらに強く当てはまる。**表現力の増加それ自体を成功指標にしない、という本提案の立場を、この一点において最も強く適用する。**

## 7. AMPの最小コア

### 必須(AMPの存在意義に直結)

| 要素 | 根拠 |
|---|---|
| `refs`によるentity参照(カタログID解決) | §4「entity reference」で確認した唯一の実証済み優位性 |
| `act`(発話行為の分類) | minimal-form-experimentで「tenseが無くてもactだけで意味の大半が伝わる」ことを確認済み |
| `predicate`(lemma+tense+polarity)+`agent`/`patient`/`recipient` | Phase1/2で実証されたSVO骨格。実験Aでtense/polarityの完全保持を確認 |
| envelope(id/conversation/sender/receiver/timestamp/in_reply_to) | 複数ターンの構造化通信を成立させる最低限の基盤 |
| ADR-023(構文の曖昧性排除≠内容の真偽) | フィールドではなくメタ原則。AMPの責務境界を定め、B群項目(相互運用性未検証等)を「未解決のまま出荷してよい」と言える根拠そのもの |

### あれば有用(コアとは言い切れない)

| 要素 | 根拠 |
|---|---|
| `attitude`(confidence/evidence/necessity) | MAGIのような合議・意思決定文脈で有用性実証済みだが、Phase1の単純な往復では一度も必要にならなかった |
| `aspect`(progressive/perfect) | 状態追跡が要るシナリオでのみ有用 |
| `clause`(深さ1の埋め込み節) | `recommend`型のact(命題を目的語に取る)でのみ有用 |
| `props`/`measurements` | 属性を持つentityを扱う場合のみ有用、実データは現在1件のみ |
| `condition`(検討中、§5) | 有用性の証拠は強いが検証段階 |

### AMPの責務外(自然言語・上位プロトコル・AIの推論・外部システムに委ねる)

| 要素 | 委ね先 |
|---|---|
| tone/nuance、丁寧さ | 自然言語(そもそも保持しないことが実験Cで価値と確認された) |
| 語用論的動機の解釈 | 受信側AIの推論(l3-matrix/cross-model-verificationでモデル間の解釈基準自体が割れることを確認済み) |
| 比喩・皮肉・婉曲表現 | 自然言語。字義通りでない意味はAMPの設計目標に含まれない(foundational-doubts #19) |
| 内容の真偽検証、署名、レピュテーション | 上位プロトコル(ADR-023が明示的に線引き) |
| メッセージ順序保証、トランスポート | トランスポート層(open-issues R-1、未解決のまま今は解かない) |
| handshake・語彙合意 | 第二の独立実装が現れるまで運用側のカタログ事前共有に委ねる(判断1) |
| 世界知識、記号接地(entityの実体が何か) | カタログ+共有された運用上の合意(記号接地問題はAMP固有の欠陥ではなく自然言語も共有する原理的限界、[接地]判定) |
| 論理演算(AND/OR/NOT)、条件の入れ子 | 自然言語、または複数メッセージへの分解。§5/§6で明確に拒否 |

## 8. 「追加しない」という結論の一覧(再掲)

- tone/nuance の構造化 → 追加しない(実験Cが示す収束の価値を損なうため)
- 語用論的動機の構造化 → 追加しない(モデル間でも解釈基準が割れる、[圏外])
- 比喩・皮肉・婉曲表現 → 追加しない(そもそも設計目標に含めない)
- AND/OR/NOT/IF/ELSE/UNLESS/XOR等の論理演算子一式 → 追加しない(実例ゼロ、プログラミング言語化のリスク、§6)
- conditionの入れ子(condition内condition) → 追加しない(実例ゼロ)
- 否定と情報不在の区別、命題status区分 → 追加しない(ADR-024で既に撤回済み、新しい実例なし)
- 動詞ごとに異なるroleフレーム(FrameNet的拡張) → 追加しない(実例ゼロ)
- 複合speech act(1メッセージ複数act) → 追加しない(実例ゼロ)
- 自己申告値(confidence等)の検証機構 → AMPに追加しない(上位プロトコルの責務、ADR-023)

## 9. 最終結論

### 1. AMPの現在の強み

- **entity参照の一意性**が、自然言語で参照手がかりが競合する状況において構造的な優位性を持つことが、独立した6本の実験群(F/F-2/G/level-difficulty-scaling/L3-matrix/cross-model-verification)で再現された。これがAMPの唯一かつ最も頑健な「自然言語より優れる」根拠
- 表現揺れの正規化(実験C: 4つの言い回し→100%同一構造への収束)
- act語彙による発話行為の明示(request/commit/query等の混同を構造的に防止)
- tense/aspect/polarityの一貫した保持(実験A: 4/4往復で無誤読)
- 自己検証性——仕様違反を検出して拒否する。v1.0 Phase2で`attitude`の配置ミスを実際に検出した実例あり
- 保証範囲の明文化(ADR-023: 構文の曖昧性排除≠内容の真偽)という設計哲学そのものが、他の未解決項目を「AMPの責務外」として切り分ける基盤になっている

### 2. AMPの現在の弱み

- 条件・従属節(until/after/if)を表現できず、日常的な指示文の多くにこれが紛れ込むため、当初の想定より支配的な制約になっている(実験B)
- urgency等、スキーマに受け皿のない情報は変換の入口で正直に失われる(実験A)
- 単一実装のみのため、フィールド解釈の同一性・相互運用性が原理的に未検証(判断書の核心的な限界、[検証不能]カテゴリ全般)
- be動詞+補語のような基本構文が欠けている(dogfooding round2)
- 実運用データが依然限定的——7 act中6 actが実データではdogfooding round2の1回のみ

### 3. AMPが自然言語より優れる条件

複数の候補entityが存在し、自然言語による参照解決に競合する手がかり(直近性など)が存在し、その表面的な手がかりが正解と一致しない状況。これは特定モデル(Sonnet)固有の現象ではなく、Sonnet・Geminiの2モデルで再現する構造的性質(cross-model-verification)。

### 4. AMPが自然言語より劣る条件

- 条件・従属節・時系列関係を伝える必要がある場合(実験B/D/G試行2)
- urgency・態度・ニュアンスなど話者の情緒的シグナルを伝える必要がある場合(実験A)
- 比喩・皮肉・婉曲・語用論的動機など、字義通りでない意味を伝える必要がある場合([圏外]カテゴリ)

### 5. 現時点で維持すべき仕様

`refs`一本化(ADR-021)、7 act語彙(ADR-011)、3role固定(agent/patient/recipient)、tense/polarity/aspect(v0.1+v0.2)、attitude(v0.2)、clause深さ1(v0.2)、ADR-023/024の保証範囲宣言。いずれも変更提案なし。

### 6. 実験すべき仕様

- **condition**: `type: "after"`/`"if"`での追試(experiment-e自身の次アクション)
- **urgency**: 最小構造候補(例: 3値程度の簡素な緊急度)をまず設計し、削除実験で効果を測定
- **time role**: 「事象時刻 vs メッセージ送信時刻」の区別という最小の切り口のみ(gap-analysisの提言どおり、time role全体は依然範囲外)

### 7. 追加候補

`condition: {type: "until"|"after"|"if", clause: {predicate, roles}}` — 既存`clause`構造の再利用、新規構文要素なし、深さ1、AND/OR/NOT無し。**最有力候補だが、仕様化はtype別の追試完了後に限る。**

### 8. 追加すべきでない機能

AND/OR/NOT/IF/ELSE/UNLESS/XOR等の論理演算子一式、conditionやclauseの入れ子(深さ2以上)、tone/nuance/丁寧さの構造化、語用論的動機の構造化、比喩・皮肉表現、自己申告値の検証機構、動詞ごとの可変roleフレーム、複合speech act。

### 9. AMPの最小コア

§7参照。必須は「refs参照・act・predicate+3role・envelope・ADR-023」の5点のみ。attitude/aspect/clause/props/conditionは「あれば有用」の層であり、コアの定義に含めない。

### 10. 今後の実験ロードマップ

1. **condition**: `type="after"`/`"if"`の削除実験を追加実施 → 複数type間で汎用的に機能するか確認 → ADR-026候補として正式化を検討(experiment-eの続き)
2. **urgency**: 最小構造候補(例: `urgency: "immediate"|"normal"|"low"`程度)を設計 → 削除実験で効果測定
3. **time role**: 「事象時刻 vs メッセージ送信時刻」の区別だけを先に決める(gap-analysisの提言どおり、time role全体からではなく最小の切り口から)
4. **be動詞+補語構文**: dogfooding round2で発見された限界の実例をもう数件集めてから対応要否を判断
5. **第二の独立実装**: 判断書が言う「本当の実用化条件」に向け、独立実装への呼びかけを継続(v1.0-phase2 Final Decisionと一致、README「独立実装、歓迎します」を参照)
6. **削除実験プロトコル自体の継続**: 「新フィールドを追加する前に、それを削った/加えた最小形で実際に会話させ、AI自身が申告する精度低下/回復を観察する」という手法を、今後の全ての仕様拡張判断の標準手続きとして維持する

## 補記: AMPの適用範囲を狭めるべき可能性について

最重要事項として、AMP自体が不要になる可能性・適用範囲を狭めるべき可能性も指摘しておく。

6本の実験群が示した「AMPが自然言語より優れる条件」は、結局のところかなり狭い——**「複数の候補entityが存在し、自然言語の参照手がかりが競合する」という1つの条件に収斂している。** それ以外の次元(urgency、condition、tone、pragmatic meaning)ではAMPは自然言語に劣るか、あるいは対応する構造を持たない。

これは「AMPは失敗している」ということではない。むしろ判断書・ADR-024が最初から取ってきた縮小志向と一致する結果であり、**「AI間の汎用通信プロトコル」を目指すのではなく、「entity参照が競合しうる文脈でのみ挿入する、軽量な参照一意化レイヤー」として適用範囲をむしろ明示的に狭める**、という方向性が今回の全実験を通観すると最も裏付けが強い。この場合、AMPは会話全体をJSON化するプロトコルではなく、自然言語の会話の中で「どのfileか」「どのagentか」が曖昧になりうる箇所にだけ埋め込む注釈(例えば`patient.refs`だけを持つ最小メッセージ)として運用する、という狭いスコープの再定義が次の実験対象になり得る。これも「追加しない」と同じ精神で、遠慮なく次の検討候補として記録する。
